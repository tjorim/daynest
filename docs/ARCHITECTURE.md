# Architecture

How the code is organised. The same layout is used in champagnefestival, daynest, travel and worktime, so a developer who
knows one of them finds things in the same place in the others. Only the feature (domain) folders differ.

## Frontend (`frontend/src/`)

```
main.tsx, env.d.ts      entry point and ambient types; nothing else lives loose in src/
app/                    bootstrap and app shell: providers, router (route tree, lazy pages), layout, pwa, theme
features/<domain>/      one folder per business domain: pages (*Page.tsx), components used only there, hooks,
                        feature-only helpers and types, and the API calls of that domain
components/             shared UI used by two or more features; components/ui/ holds the design-system primitives
lib/                    framework-agnostic helpers and the HTTP client (lib/api/); no `utils/` folder
mocks/                  MSW handlers and fixtures (fixtures are typed with the generated API types)
config/                 runtime configuration and constants
types/                  UI-only types (never API shapes)
i18n/                   Paraglide glue          paraglide/   compiled messages (generated)
styles/                 global CSS (tailwind.css, app.css)
api-schema/             generated by Orval, never edited   api-types.ts   the single import point for API shapes
```

Rules:

- A folder under `features/` is named after the product domain, in kebab-case. Split one that grows past about 40 files
  into sub-folders by sub-area.
- Code used by one feature stays in that feature. Move it to `components/`, `hooks/` or `lib/` only when a second feature
  needs it.
- Import across folders with the `@/` alias (`@/features/today/...`); use relative imports only inside one feature folder.
- API shapes come from `@/api-types` (generated types). Never declare an API response type by hand.
- Component files are `PascalCase.tsx`, hooks `useThing.ts`, other modules `camelCase.ts`.
- Tests live in `frontend/tests/` and mirror the `src/` path (`src/features/today/TodayPage.tsx` is covered by
  `tests/features/today/TodayPage.test.tsx`); shared helpers are in `tests/utils/`. End-to-end specs are in `frontend/e2e/`.

### Daynest features

`auth`, `calendar`, `legal`, `meal-planning`, `medication`, `pebble`, `search`, `settings`, `shopping`, `stats`,
`templates`, `today`.

## Backend (`backend/app/`)

```
main.py                 app assembly: middleware, router registration, lifespan; nothing else
mcp_server.py           the stdio MCP entry point (`python -m app.mcp_server`), documented in backend/docs
openapi_export.py       writes frontend/openapi.json (`uv run python -m app.openapi_export`)
routers/                the HTTP layer, one module per domain; thin: validate, call a service, return a response model
  dependencies/         FastAPI dependencies shared by the routers (auth, audit, events, integration auth)
  integrations/         routers for the integration clients (Home Assistant, Pebble, client management)
services/               business logic, one module per domain
repositories/           database access used by the services
models/                 SQLAlchemy models, one module per domain
schemas/                Pydantic request and response models, one module per domain (`base.py` has the shared bases)
core/                   configuration, errors, OIDC, password hashing, pagination, request limits and timing, observability
db/                     engine, session, base class and the dev schema helper
mcp/                    the MCP server, tools and resources
middleware/             ASGI middleware
```

Rules: every JSON route declares a response model; routers do not touch the database directly; code used by one domain
stays in that domain's modules. Tests live in `backend/tests/`. The shared target for all four apps is this layout
(`main.py`, `core/`, `db/`, `models/`, `schemas/`, `routers/`, `services/`, `mcp/`, `middleware/`); `repositories/` is
kept here because daynest already has it.
